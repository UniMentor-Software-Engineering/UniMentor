## 4. Project Structure and Integration

This section outlines the foundational architecture, repository structure, dependency management, and core integrations established during Phase 1 to ensure a robust and maintainable development environment for the UniMentor platform.

### 4.1. Repository Skeleton and Layered Architecture

To promote separation of concerns and maintainability, the Node.js/Express backend has been organized using a strict layered architecture pattern. The repository is structured into the following core directories:

*   **`routes/`**: Acts as the entry point for incoming HTTP requests. It defines the API endpoints and maps them to the corresponding controllers. It handles route-specific middleware (like authentication checks).
*   **`controllers/`**: Responsible for extracting parameters from the request (`req`), calling the appropriate service methods, and formatting the HTTP response (`res`). It contains no business logic.
*   **`services/`**: The core of the application where all business rules and use case logic are executed. Services coordinate between different repositories to perform complex operations.
*   **`repositories/`**: The data access layer. It encapsulates all direct interactions with the PostgreSQL database, separating the SQL queries from the business logic.

### 4.2. Dependency Management (npm)

In the Node.js ecosystem, we utilize **npm** (Node Package Manager) as our dependency management tool, serving the equivalent purpose of Maven or Gradle in Java environments.

*   **`package.json`**: This file acts as the manifest for the project. It contains metadata about the project, scripts for running/testing the application, and the lists of required packages.
*   **`package-lock.json`**: This file is automatically generated and locks the exact versions of the dependencies (and their sub-dependencies) installed. This guarantees that all developers and the deployment environments run the exact same code, preventing "it works on my machine" issues.
*   **Dependencies vs. devDependencies**:
    *   `dependencies`: Packages strictly necessary for the application to run in production (e.g., `express`, `pg` for PostgreSQL, `jsonwebtoken`).
    *   `devDependencies`: Tools only needed during local development or in the CI/CD pipeline (e.g., `eslint`, `jest`, `nodemon`). These are not installed in the final production build.
*   **Semantic Versioning (SemVer)**: We adhere to the SemVer standard (`MAJOR.MINOR.PATCH`). In our `package.json`, we use prefixes to control updates:
    *   The caret (`^`): Allows updates to minor and patch versions, but prevents breaking major updates (e.g., `^1.2.3` allows `< 2.0.0`).
    *   The tilde (`~`): Restricts updates only to the latest patch version (e.g., `~1.2.3` allows `< 1.3.0`).

### 4.3. Core Configurations and Frontend Integration

To establish a solid baseline before implementing specific use cases, several core configurations were set up:

*   **Database Connection**: Initialized the connection pool to the PostgreSQL database using the `pg` library, ensuring efficient reuse of connections.
*   **Global Error Handling Middleware**: Implemented a centralized error-handling middleware in Express. This catches unhandled exceptions across all routes and returns standardized JSON error responses, preventing the server from crashing unexpectedly.
*   **Frontend `api.js` Module**: Created a shared `api.js` utility for the vanilla JavaScript frontend. This module abstracts the `fetch` API calls. Crucially, it configures `credentials: 'include'` for all requests, which is mandatory for our chosen authentication strategy (ADR 1: HttpOnly Cookies) to work correctly across domains.
*   **Base CSS**: Defined the global CSS variables and base styles (reset, typography, color palette) to ensure UI consistency from the start.

### 4.4. Quality Assurance and CI/CD

To maintain code quality and automate the deployment process:

*   **ESLint**: Configured to enforce coding standards and catch potential errors statically before execution.
*   **Jest**: Integrated as the testing framework for future unit and integration tests.
*   **GitHub Actions**: A Continuous Integration (CI) pipeline was established. Upon every push or Pull Request to the `main` branch, GitHub actions automatically run ESLint and the Jest test suite to ensure no broken code is merged.
*   **Deployment Architecture**:
    *   **Frontend**: Automatically deployed and hosted on **Vercel**, benefiting from its global CDN for static HTML/CSS/JS files.
    *   **Backend**: Automatically deployed and hosted on **Render** as a Node.js web service, connected to our managed PostgreSQL instance.
